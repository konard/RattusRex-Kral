# План контейнеризации проекта через Docker

> Технический план внедрения Docker для веб‑приложения **Epoch of Catastrophe
> Assistant** (управление игровым сервером D&D). Документ подготовлен в рамках
> задачи [#53](https://github.com/RattusRex/Kral/issues/53).

Документ содержит:

1. Анализ текущей архитектуры (backend, frontend, БД, инфраструктура).
2. Что блокирует контейнеризацию сейчас.
3. Рекомендуемую структуру контейнеров.
4. Перечень файлов, которые нужно создать и изменить, и порядок внедрения.
5. Обязательные изменения и изменения «на потом».
6. Риски и технические ограничения.

Готовые конфигурации, описанные в плане, уже добавлены в репозиторий:
`docker-compose.yml`, `docker/backend.Dockerfile`, `docker/frontend.Dockerfile`,
`docker/nginx.conf`, `.dockerignore`. Инструкция по запуску — в
[README](../README.md#docker-deployment).

## 1. Анализ текущей архитектуры

### 1.1 Backend

| Параметр | Значение |
| --- | --- |
| Фреймворк | FastAPI `0.115.6` (Starlette), ASGI‑сервер `uvicorn 0.34.0` |
| Точка входа | `app.main:app` |
| Запуск (dev) | `uvicorn app.main:app --reload --host 0.0.0.0 --port 8000` |
| Запуск (prod) | `uvicorn app.main:app --host 0.0.0.0 --port 8000` |
| Зависимости | `requirements.txt` (FastAPI, SQLAlchemy 2.0, psycopg/psycopg2, bcrypt, python‑jose, …) |
| Конфигурация | переменные окружения + чтение `.env` собственным загрузчиком `app/core/env.py` |
| Аутентификация | JWT (HS256), подпись ключом `SECRET_KEY` |
| Статические данные | `magicvariants.json` (~80 КБ) читается из корня проекта в `app/api/inventory.py` |

**Чтение конфигурации.** `app/core/env.py:load_env()` ищет `.env` вверх по дереву
каталогов и заполняет `os.environ`, **не перезаписывая** уже заданные переменные.
Это значит, что переменные, переданные через Docker (`environment:` в compose),
имеют приоритет над файлом `.env` — файл внутри контейнера не нужен.

**Обязательные переменные окружения** (без них backend не стартует):

- `DATABASE_URL` — строка подключения к PostgreSQL; для контейнера она должна
  указывать на хост `db`;
- `SECRET_KEY` — `app/core/security.py` бросает `RuntimeError`, если ключ пуст;
- `ADMIN_PASSWORD` — `app/main.py` бросает `RuntimeError`, если пароль пуст;
- `ALLOWED_ORIGINS` — список CORS‑origin через запятую (может быть пустым, но
  тогда фронтенд с другого origin получит ошибку CORS).

**Готовность к контейнеру:** высокая. Сервер уже слушает `0.0.0.0:8000`,
конфигурация полностью через окружение, нет записи в локальную ФС, кроме чтения
`magicvariants.json`. Особых доработок кода не требуется.

### 1.2 Работа с базой данных и миграции

- ORM — SQLAlchemy 2.0 (`app/db/database.py`).
- Схема создаётся **автоматически** на старте в `lifespan`:
  `Base.metadata.create_all(bind=engine)`.
- Дополнительно выполняются «ручные» миграции в `ensure_schema_columns()` —
  идемпотентные `ALTER TABLE ... ADD COLUMN` через `inspect(engine)` (добавление
  `temp_hp`, `speed`, `game_created_at`, `inventories.notes`, миграция роли из
  legacy `is_admin`).
- **Alembic отсутствует.** Версионирования схемы нет — это работает для простого
  добавления колонок, но не масштабируется на удаление/переименование колонок и
  откаты.
- На первом старте создаётся учётная запись `admin` (роль `owner`) с паролем из
  `ADMIN_PASSWORD` (`seed_admin()`).

### 1.3 Frontend

| Параметр | Значение |
| --- | --- |
| Стек | React 18 + Vite 6 + TypeScript + Tailwind |
| Корень исходников | `app/frontend` (`index.html`), алиас `/src` → `app/src` |
| Сборка | `npm run build` → `tsc && vite build`, выход в `dist/` |
| Dev‑сервер | Vite, проксирует `/api` на `http://127.0.0.1:8000` (`VITE_API_TARGET`) |
| Базовый URL API | вычисляется в `app/src/apiBase.ts` |

**Резолвинг базового URL API** (`resolveApiBaseURL`):

- если задан `VITE_API_BASE_URL` — используется он;
- в production‑сборке, если задан `VITE_API_TARGET`, берётся `<target>/api`;
- иначе по умолчанию — относительный префикс **`/api`**.

Ключевой вывод: при развёртывании, где фронтенд и API находятся **на одном
origin** (фронтенд‑nginx проксирует `/api` на backend), бандл не требует никакой
сборочной конфигурации — дефолтный `/api` работает «из коробки», CORS не
задействуется. Именно эта схема выбрана в `docker-compose.yml`.

**Нужен ли nginx:** да. Vite‑сборка — это статические файлы; их нужно чем‑то
раздавать. nginx одновременно (а) отдаёт статику с SPA‑fallback на `index.html`
и (б) проксирует `/api` на backend, давая единый origin.

### 1.4 База данных — текущее состояние

> ⚠️ Важное уточнение к постановке задачи: проект **уже использует PostgreSQL**,
> а не SQLite. SQLite применяется только в тестах (`tests/test_api.py` ставит
> `DATABASE_URL=sqlite://` in‑memory). Поэтому пункт «переход с SQLite на
> PostgreSQL» из раздела «желательно улучшить» **уже выполнен** в продакшен‑коде
> и в контейнеризации не требуется.

- Драйверы в `requirements.txt`: `psycopg` (3.x) и `psycopg2-binary`/`psycopg-binary`.
  SQLAlchemy для `postgresql://` по умолчанию использует `psycopg2`.
- Для локальной разработки строка подключения задаётся явно через
  `DATABASE_URL` в `.env` или в окружении. Неявного дефолта в коде нет.
- **Docker Volume нужен** для каталога данных PostgreSQL
  (`/var/lib/postgresql/data`), иначе данные теряются при пересоздании
  контейнера. В `docker-compose.yml` для этого заведён именованный том `pgdata`.

### 1.5 Инфраструктура и публикация

- Сейчас публикация описана как Cloudflare Tunnel, но конфигурации в репозитории
  нет.
- Cloudflare Tunnel удобно контейнеризовать отдельным сервисом
  (`cloudflare/cloudflared`) с токеном туннеля — не нужно открывать входящие
  порты на хосте/VPS.

## 2. Что блокирует контейнеризацию прямо сейчас

| # | Проблема | Критичность | Решение |
| --- | --- | --- | --- |
| 1 | В контейнере `DATABASE_URL` должен указывать на сервис `db`, а не на `localhost` | Блокирует | Передавать строку подключения через `environment` в compose (сделано) |
| 2 | Пароли PostgreSQL и другие секреты должны задаваться вне кода | Высокая (безопасность) | Брать пароль из `.env`/секретов, не хардкодить (см. §6) |
| 3 | Нет Dockerfile, docker-compose.yml, .dockerignore | Блокирует | Добавлены в рамках задачи |
| 4 | `requirements.txt` сохранён в кодировке **UTF‑16 LE с BOM** | Средняя | Современный pip читает (auto‑decode по BOM), но многие инструменты/линтеры ломаются. Рекомендуется пересохранить в UTF‑8 (см. §5) |
| 5 | `requirements.txt` содержит тяжёлые dev‑зависимости (ipython, jupyter, nbconvert, matplotlib‑inline, pipreqs, sentry‑sdk…) | Средняя | Раздуают образ и время сборки. Желательно разделить runtime/dev зависимости (см. §5) |
| 6 | `magicvariants.json` обязателен в рантайме и резолвится от корня проекта | Низкая | Учтено: файл копируется в `/app/magicvariants.json` в backend‑образе |
| 7 | Схема и сид‑данные создаются на старте приложения, нет отдельного шага миграций | Низкая/Средняя | Работает для текущей модели; для продакшена желателен Alembic (см. §5) |

## 3. Рекомендуемая структура контейнеров

```text
                 Internet
                    │
                    ▼
          Cloudflare Tunnel            (необязательный сервис cloudflared)
                    │
                    ▼
        ┌──────────────────────┐
        │  frontend (nginx)    │  :80  → host :8080
        │  - статика dist/     │
        │  - /api → backend    │
        └───────────┬──────────┘
                    │ /api
                    ▼
        ┌──────────────────────┐
        │  backend (FastAPI)   │  :8000 → host :8000 (для /docs, опц.)
        │  uvicorn, N воркеров  │
        └───────────┬──────────┘
                    │ SQLAlchemy
                    ▼
        ┌──────────────────────┐
        │  db (PostgreSQL 16)  │  :5432 (только внутр. сеть)
        │  volume: pgdata      │
        └──────────────────────┘
```

**Почему три сервиса:**

- **frontend (nginx)** — раздаёт собранный SPA и служит единой точкой входа,
  проксируя `/api` на backend. Это убирает проблему CORS и не требует
  конфигурации API‑URL в бандле.
- **backend (FastAPI/uvicorn)** — бизнес‑логика и API. Многопроцессность через
  `--workers` (`WEB_CONCURRENCY`).
- **db (PostgreSQL)** — данные в именованном томе `pgdata`, переживают
  пересоздание контейнеров.

**cloudflared** добавлен как опциональный сервис под профилем `tunnel`, чтобы не
требовать токен в обычном локальном запуске.

## 4. Перечень файлов: что создать и что изменить

### 4.1 Создать

| Файл | Назначение |
| --- | --- |
| `docker/backend.Dockerfile` | Образ backend: python:3.11‑slim, установка зависимостей, запуск uvicorn, непривилегированный пользователь, healthcheck |
| `docker/frontend.Dockerfile` | Многоступенчатый образ: сборка Vite (node:20‑alpine) → раздача nginx |
| `docker/nginx.conf` | Конфиг nginx: статика + SPA‑fallback + reverse‑proxy `/api` |
| `docker-compose.yml` | Оркестрация `db` + `backend` + `frontend` (+ `cloudflared` по профилю) |
| `.dockerignore` | Исключение `.git`, `.venv`, `node_modules`, `dist`, `.env`, docs из контекста сборки |

### 4.2 Изменить

| Файл | Изменение |
| --- | --- |
| `README.md` | Добавлен раздел **Docker Deployment** с пошаговой инструкцией |
| `.env.example` | Добавлены `POSTGRES_USER/PASSWORD/DB`, заметки про `ALLOWED_ORIGINS`, `WEB_CONCURRENCY`, `CLOUDFLARE_TUNNEL_TOKEN` |
| `docs/docker-plan.md` | Этот документ |

### 4.3 Порядок внедрения

1. `.dockerignore` — минимизировать контекст сборки.
2. `docker/backend.Dockerfile` — собрать и проверить образ backend в одиночку.
3. `docker/frontend.Dockerfile` + `docker/nginx.conf` — собрать фронтенд.
4. `docker-compose.yml` — связать сервисы, добавить healthcheck'и и том БД.
5. Обновить `.env.example` и `README.md`.
6. (Желательно, позже) добавить Alembic, CI‑сборку образов, бэкапы БД.

## 5. Обязательные и желательные изменения

### 5.1 Обязательные (для рабочей контейнеризации)

- Передавать `DATABASE_URL`, `SECRET_KEY`, `ADMIN_PASSWORD`, `ALLOWED_ORIGINS`
  через окружение/секреты (реализовано в compose).
- Том для данных PostgreSQL (`pgdata`).
- `magicvariants.json` в backend‑образе (реализовано).
- Healthcheck'и и `depends_on: condition: service_healthy` для корректного
  порядка старта (реализовано).

### 5.2 Желательные (можно позже)

- **Кодировка `requirements.txt`:** пересохранить в UTF‑8 без BOM. Сейчас файл в
  UTF‑16 LE; современный pip справляется, но это хрупко и ломает многие
  инструменты.
- **Разделение зависимостей:** вынести dev/notebook‑пакеты (ipython, jupyter,
  nbconvert, matplotlib‑inline, pipreqs, sentry‑sdk и т.п.) в отдельный
  `requirements-dev.txt`, оставив в рантайм‑образе только необходимое — это
  заметно уменьшит размер образа и время сборки.
- **Alembic:** ввести версионируемые миграции вместо `create_all` +
  ad‑hoc `ALTER TABLE`, добавить шаг `alembic upgrade head` в entrypoint или
  отдельный одноразовый сервис.
- **CI/CD:** сборка и публикация образов (GitHub Actions → GHCR), прогон
  `pytest`/`npm test`/`npm run build` на PR.
- **Резервное копирование БД:** регулярный `pg_dump` (cron‑сервис или внешний
  планировщик) с выгрузкой в защищённое хранилище.
- **Production WSGI/ASGI:** при росте нагрузки — gunicorn с uvicorn‑воркерами
  (требует добавить `gunicorn` в зависимости; сейчас его нет, поэтому в образе
  используется uvicorn `--workers`).
- **Секреты:** перейти на Docker/Swarm secrets или внешний менеджер секретов
  вместо переменных окружения в открытом `.env`.

## 6. Риски и технические ограничения

| Риск | Описание | Митигизация |
| --- | --- | --- |
| Отсутствует `DATABASE_URL` | Backend и dev launcher не стартуют без явной строки подключения | Создать `.env` из `.env.example` и задать пароль БД там; в Docker строка подключения строится из `POSTGRES_*` |
| Утечка секретов | `.env` содержит `SECRET_KEY`, `ADMIN_PASSWORD`, пароль БД | `.env` уже в `.gitignore` и в `.dockerignore`; не коммитить, в продакшене — секрет‑менеджер |
| CORS / origin | При неверном `ALLOWED_ORIGINS` фронтенд получит ошибки | Схема с nginx‑прокси делает запросы same‑origin; `ALLOWED_ORIGINS` всё равно нужно указать на публичный URL |
| Кодировка `requirements.txt` | UTF‑16 LE с BOM может сломать сторонний тулинг | Пересохранить в UTF‑8 (желательно) |
| Размер образа backend | Тяжёлые dev‑зависимости | Разделить зависимости (желательно) |
| Отсутствие версионируемых миграций | Нет Alembic; сложные изменения схемы рискованны | Ввести Alembic перед сложными миграциями |
| Старт до готовности БД | Backend стартует раньше PostgreSQL | `depends_on: condition: service_healthy` + healthcheck `pg_isready` (реализовано) |
| Потеря данных | Контейнер БД без тома | Именованный том `pgdata` (реализовано) + регулярные бэкапы (желательно) |

## 7. Production deployment через Cloudflare Tunnel

1. Создать туннель в Cloudflare Zero Trust (Networks → Tunnels), получить токен.
2. Настроить public hostname туннеля на сервис `http://frontend:80` (внутри
   compose‑сети) — тогда наружу не нужно открывать порты.
3. Положить токен в `.env` как `CLOUDFLARE_TUNNEL_TOKEN`.
4. Запустить с профилем туннеля:
   ```bash
   docker compose --profile tunnel up -d --build
   ```
5. Указать публичный домен в `ALLOWED_ORIGINS` (например,
   `https://kral.example.com`).

**Переход на VPS / домашний сервер:** тот же `docker-compose.yml` переносится
без изменений; различается только `.env` (домен, секреты). Для домашнего сервера
Cloudflare Tunnel особенно удобен — не нужен белый IP и проброс портов.
